# The conf-dir Layout

A *conf-dir* is the directory `gl` reads from when building. Everything declarative about a particular set of packages and a particular rootfs lives here. Everything content-addressed — tarball blobs, build outputs, lockfile indexes — lives in the object store, which is separate.

## Anatomy

```
<conf-dir>/
├── pkgs/
│   ├── bash/
│   │   ├── sources.yml          # generated by gl import
│   │   ├── src/                 # generated by gl import
│   │   │   └── debian/
│   │   ├── build.yml            # YOU write this
│   │   └── build-deps.yml       # generated by gl lockfile
│   ├── glibc/
│   │   └── ...
│   └── ...
├── rootfs.yml                   # YOU write this
└── rootfs-deps.yml              # generated by gl lockfile-rootfs
```

Three categories of file:

| Kind | Source | What it carries |
|------|--------|----------------|
| Hand-edited | You | `build.yml`, `rootfs.yml` |
| Tool-generated | `gl import`, `gl lockfile` | `sources.yml`, `src/`, `build-deps.yml`, `rootfs-deps.yml` |
| Pure pointer | Object store, by hash | `<orig.tar.*>`, lockfile blobs, `.deb` blobs |

You commit the first two categories to version control. The third lives in the object store at `~/.cache/gl-ng` (or wherever `--cache` points).

## Per-package files

### `pkgs/<name>/sources.yml`

Generated by `gl import`. References original upstream tarballs by content-address hash:

```yaml
sources:
  - name: glibc_2.40.orig.tar.xz
    hash: 0b89b8c058eaa0f1121a814be6196ce2048235b43d95714ce8278fe72c7cc34a
```

Multiple entries are normal — some packages (e.g. Perl) have multiple component tarballs.

### `pkgs/<name>/src/`

Generated by `gl import`. Contains the source tree:

- For 3.0 (quilt) and 1.0 packages: `src/debian/` only. The orig tarball is bind-mounted at build time.
- For 3.0 (native) packages: the entire upstream tree.

### `pkgs/<name>/build.yml`

Hand-edited. The full reference is on [Writing build.yml](./build-yml.md). Quick sketch:

```yaml
build_profiles: [nocheck, noudeb]
build_options: [nocheck]
depends: [glibc:libc6-dev, ncurses:libncurses-dev]
runtime_depends:
  somebinary: [other-source:other-binary]
lockfile_deps:
  somebinary: [linux-libc-dev]
extra_build_env:
- "DEB_CFLAGS_APPEND=-Wno-error"
```

### `pkgs/<name>/build-deps.yml`

Generated by `gl lockfile`. Per-architecture pointer to a lockfile blob:

```yaml
amd64: 9209690faf8b2b09cb02be917387a121be291af320548a1600b5105bc646be53
arm64: fb81856a93eb6572d2c9e43c06a52c7cc17f47506dee98059ab90c8240444abb
```

The blob in the store is a deb822 `Packages` index with every binary `.deb` needed to assemble the build chroot, frozen at the time of generation.

## Top-level files

### `rootfs.yml`

Hand-edited. Lists the *direct* packages in the rootfs:

```yaml
packages: [base-files:base-files, base-passwd:base-passwd, coreutils:coreutils, bash:bash, gcc-16:libgcc-s1]
```

Each entry is `<source-package>:<binary-package>`. Transitive runtime dependencies are computed by the engine — you do *not* list libc6, libssl3t64, etc., even though they appear in the final image. See [Writing rootfs.yml](./rootfs-yml.md).

### `rootfs-deps.yml`

Generated by `gl lockfile-rootfs`. Same shape as `build-deps.yml` — a per-arch hash pointing to a deb822 blob. Captures the *Debian tooling* used during rootfs configuration (`dpkg`, `perl`, `mawk`). These tools are present on the build host's overlay during configuration but are *not* shipped in the final rootfs.

## Auto-discovery

If you run `gl build` without `--conf-dir`, the CLI walks up from the current directory looking for the first ancestor that has both a `pkgs/` directory and a `rootfs.yml` file. This is convenient for shell history but explicit `--conf-dir <path>` is recommended in scripts.

## Multiple conf-dirs and a shared cache

The cache is per-user, not per-conf-dir. If you have several conf-dirs sharing the same architecture, they share imported blobs and lockfile blobs through the object store. Different conf-dirs producing different rootfs identities populate distinct entries in `map/` but reuse `.deb` blobs whenever the inputs match.

This is an intentional design point: switching between branches with different `build.yml` contents is cheap because most blobs are already there.

## Templates

The repo ships a set of templates for the e2e test at `tests/templates/`. Each subdirectory is a package name, holding a `build.yml` ready to be copied into a freshly imported `pkgs/<name>/`:

```
tests/templates/
├── bash/build.yml
├── coreutils/build.yml
├── ...
└── rootfs.yml
```

The `prepare_staging.sh` script automates: importing each template's named package, copying the template `build.yml` in, generating its lockfile, and then doing the rootfs lockfile. After it finishes, the resulting directory is a fully populated conf-dir. See [End-to-End Walkthrough](./e2e.md).
